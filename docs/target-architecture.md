# Целевая архитектура

## Один сервер и существующее ядро

```text
Классический DOM-клиент ─┬─ LocalTransport ───────────────────────┐
                        └─ WebSocketTransport → Node /ws ───────┤
                                                 │              │
                                     сессия → комната → Table → Game
                                                 │              │
                                            каталог комнат      ├→ проекция на место
                                                                └→ события → статистика
```

- **`src/rules`** — каталог, раздача, правила и типизированные доменные события. **`src/match`** — матч, фазы, команды, боты, логические часы. Сохранить пути. Проверять, что ни один модуль ядра не импортирует клиент или WebSocket.
- **`src/shared`** — версия протокола, типы и проверяемые JSON-сообщения, разрешённое представление игрока, чистые функции для локальной подсказки. Действия домена и сетевые конверты остаются разными типами.
- **`server`** — отдельный Node-процесс, HTTP health и WebSocket, сессии, каталог комнат, расписание, адаптер статистики. `Room` владеет одним `Table` и привязкой `Session → Seat`. Таблица определяет результат, а комната отвечает за доступ и порядок.
- **`src/classic`** — HTML/CSS и текущая оболочка, клиентское хранилище проекции, ввод и два транспорта. **`src/ui`** — отладочная оболочка. Обе могут читать общий контракт, сохраняя свои компоненты и локальный режим.
- **`tools` и `tests`** — seed-симулятор, локальные WebSocket-интеграции, нагрузка, профилирование, экспорт. Не требуется переносить проект в workspace-пакеты.

## События, регистрации и воспроизведение

Расширять существующие каталоги `cards.ts`, `contracts.ts`, `items.ts`, `horsemen.ts`, `slots.ts` и `PRESETS` типизированными ID и узкими обработчиками. Режимы `one/debt` оформлять на уровне матча. Выносить случаи из `play.ts` только с эталоном порядка: принятие группы → изменение руки → победа → эффекты, когда они полагаются → переход хода. События описывают уже применённый результат. Для ветвлений дня/ночи и Ренты важно проверить порядок до и после выделения функции.

Сохранить внедрение генератора и `Clock`, добавить управление рабочим источником случайности. В production использовать криптографический источник случайности сервера, независимые случайные идентификаторы и версионированный внутренний replay при необходимости. Для воспроизводимых тестов фиксировать сценарий, seed, настройки, версии правил и порядок действий/срабатывания часов. Случайность ботов и служебных пауз постепенно отделять от случайности правил. Текущий вызов RNG внутри сортировки и влияние расписания на поток требуют отдельных проверок. Эталонные seeds сохранять в режиме совместимости.

## Сессии, комнаты и сетевой контракт

1. Сервер выдаёт случайный идентификатор сессии и секрет восстановления, например 32 байта энтропии. Коду приглашения отводится только поиск комнаты. Секрет возвращается только своему клиенту по TLS и не записывается в журналы, URL или экспорт. Клиент сохраняет сессию для перезагрузки страницы. Просроченная привязка аннулируется. При восстановлении новый сокет получает текущее место и снимок, старый теряет право посылать команды.
2. Комната ведёт состояние `lobby → match → over → lobby` и стабильные места. Хост задаёт видимость, вместимость, режим, лимит, пресет, ботов и старт. Настройки матча замораживаются. Отдельные команды — создание, join, resume, leave. Публичный каталог отдаёт утверждённые поля, например название, режим, статус и заполненность. Приватная комната, имена участников, скрытые правила и секреты в каталог не попадают. Вход в активную игру предусмотрен только через resume.
3. Протокол первой версии использует JSON. Конверт игровой команды содержит `v`, идентификатор команды, монотонный клиентский номер, идентификатор матча/раздачи, номер наблюдаемой ревизии и конкретное намерение. Место определяется сокетом. Сервер отвечает `ack` с результатом и актуальной ревизией. Повторить ранее подтверждённую команду можно только для получения того же подтверждения, в пределах ограниченного кэша сессии. При неизвестном старом номере нужен resync без повторного применения.
4. Команды одной комнаты, отключения и задачи таймера применяются последовательно. Снимок имеет монотонную серверную ревизию комнаты, ID раздачи и актуальный ID решения. Клиент игнорирует старые снимки. При разрыве цепочки возможен запрос полного снимка. Для взаимоисключающих ходов сверять контекст хода и устаревшую ревизию. Для независимых действий в лавке и передаче другим местом допустима более старая глобальная ревизия, если фаза та же и состояние покупателя/выбирающего валидно. Условия повторного применения и обработки ошибок описать в версии протокола.
5. Таймеры публикуют серверное время и абсолютный дедлайн соответствующего решения. Реальное исполнение опирается на монотонные часы процесса. Драфт (30 с), лавку и предложение (45 с), обычный и пропущенный ход, Войну и рулетку проверять отдельно. У задачи есть ID своего хода/фазы, после отмены она не может выполнить действие в новой фазе. Присутствие и переподключение не продлевают чужие сроки.
6. Отдельные параметры определяют льготный период места, пропуск, передачу хоста, TTL пустой комнаты и пределы активных симуляций. Ушедший остаётся на месте до истечения льготы. Дефолты миграции сверить с legacy. После срока применяется согласованное последствие, автоматической замены ботом нет. При необязательных шагах пользуемся уже существующими правилами автоответа, передачи и завершения лавки.

## Проекция и клиент

| Кому | Что получает |
|---|---|
| Игрок | Обе стороны собственных карт, стабильные ID своих карт, собственные возможности, личные предложения и шансы. Следующая активная сторона только при праве Шулера. |
| За столом | Публичное состояние, верх сброса, верхняя рубашка общей колоды, размеры рук и порядок видимых рубашек каждого соперника. Перемещение, перестановка и выбор карт в открытой руке наблюдаемы. |
| Каталог | Сводка только публичных комнат. |
| Сервер | Полное состояние, источники случайности, секреты сессий и приватные сведения. |

Собирать каждую проекцию по списку разрешённых полей, отдельно для событий и их payload. Старые позиционные кортежи создаёт клиентский адаптер из разрешённого объекта. По reconnect или при пропущенных событиях применить свежий снимок без переигрывания устаревших звуков и анимаций. Внутренняя проверка событий различает публичные, персональные и серверные. Снимки достаточно компактны для первого этапа по конструкции; пределы размера и необходимость дельт проверяются нагрузкой.

Порядок руки соперника входит в наблюдаемое состояние. Игрок может следить за перемещением видимой карты и запомнить её рубашку перед Сменой. Для жестов достаточно публичной позиции или идентификатора в пределах видимой руки. Серверные ID, скрытые лица и порядок следующих карт общей колоды остаются закрыты. Для будущих действий по чужой руке команда сможет указать видимую позицию и ревизию руки. Сервер проверит соответствие позиции и право применения эффекта. Клиентские жесты сами по себе не меняют правила или скрытые зоны. При переподключении снимок восстанавливает текущий порядок.

## Боты, ресурсы и данные

- Сохранить `nextBotJob`, магазин и выбор Bot. Доступ к полной модели заменить входом, построенным из допустимых вариантов хода и наблюдаемого состояния. Один путь исполнения поддерживает смешанные матчи и полностью ботные матчи без подключённых игроков. Для последних дать серверный и локальный запуск из инструмента, без режима наблюдения. Профили сложности используют один оценщик с коэффициентами риска, атаки, комбинаций и долга. Скорость анимации отдельно от сложности.
- Один таймер пробуждения на комнату, ближайшее событие вычисляется из очереди. Нет частого таймера при отсутствии задач. Глобальный heartbeat, лимиты открытых соединений, команд, комнат и полезной нагрузки. Медленному соединению можно заменить очередь снимков самым свежим или закрыть его с возможностью восстановления. Очистка отменяет задачки, подписки и сессионные ссылки. Ошибка комнаты переводит её в обозримый сбой, остальные продолжают работу.
- SQLite для завершённых матчей, агрегатов и компактных событий: версия правил, анонимные места матча, длительность, победа, причина поражения, карты/эффекты, комбинации, причины движения долга, покупки, сделки и фазовые переходы. Экспорт агрегатов и обезличенных записей через CLI. Ники, токены, IP, частные руки и ключи replay в экспорт не входят. Буферизированная запись короткими транзакциями, отдельно тестировать ошибку диска и закрытие.
- Плановое обновление сначала собирает новую версию. Затем сервер блокирует запуск новых матчей и ждёт завершения всех начатых. Подключение к уже начатому матчу и восстановление места продолжают работать. Пока есть хотя бы один начатый матч, версия не переключается. После завершения последнего матча сервер обновляется, проходит health-проверку и снова разрешает старты. Комнаты первого релиза остаются в памяти, восстановление после аварийного рестарта вне этого этапа.

## Зависимости и развёртывание

Сохранить Node.js, TypeScript, Vite, Playwright и `node:test`. Для сервера добавить [`ws`](https://github.com/websockets/ws), соответствующие типы и веб-API WebSocket в браузере. Проверки JSON начать с маленьких декодеров по командам. Для SQLite проверить встроенный [`node:sqlite` целевой версии Node](https://nodejs.org/api/sqlite.html) и его синхронное влияние на event loop. Решение о дополнительном драйвере отложить до замера или необходимости поддержки иной версии среды.

На VPS оставить Nginx и HTTPS на 443. Он отдаёт статику и проксирует `/ws` в локальный порт Node. 3X-UI/Xray остаётся отдельной службой. Текущий автообновлятор переключает статику. Выпуск сервера проверяет health, совместимость версии клиента и отсутствие прерывания активных матчей перед публикацией. Старые хешированные ресурсы должны оставаться доступны открытым клиентам во время переключения. Проверить TTL старых сборок и рост диска. Внешняя статистика, отдельные сервисы и новый графический пакет для первого релиза не требуются.
