# Last Deal network protocol v1

The classic table connects to the same-origin `/ws` endpoint. Nginx terminates TLS in production. The server uses `Table` for game decisions, applies messages and clock jobs sequentially per room, and sends only a projection for the bound seat.

## Requests

```json
{"v":1,"n":12,"revision":9,"game":"a-game-uuid","phase":"play","command":{"t":"act","a":{"k":"draw"}}}
```

- `create` takes `name` and optional settings. `join` takes `code` and `name`. `resume` takes a private `token`. A successful response is `joined` with `code`, `token` and `next`, followed by a current snapshot. The secret is generated by the server and stored in the browser tab's session storage. A newer connection replaces the previous one.
- `list` subscribes to `directory` updates. Entries contain the code, mode, occupancy, capacity and active status for public rooms. `settings`, `start`, `tolobby`, `addbot`, and `rmbot` require the host. `rename` changes your lobby name. `leave` forfeits the seat in a running match. `sync` requests a full snapshot.
- Settings fields are `mode`, `limit`, `rules`, `cards`, `capacity` and `public`. Capacity is 2–6. The optional bot profile is one of `standard`, `cautious`, `aggressive`, `combos`, or `debt`.
- `act.a.k` supports `play`, `draw`, `pass`, `gamble`, `roul`, `item`, `ability` and `deal`. `play` uses the owner's `id` and up to 20 `extraIds`, with optional `color`, `flipColor`, and `target`. `draft` takes `ids`; `shop` takes `a` with a purchase kind or `done`; `col` takes `k` and optional `target`. IDs are matched against the sender's own authoritative hand. The server ignores client claims about author or outcome.
- `order` takes an exact permutation of the sender's own card IDs and a subset named `selected`. It changes the visible order and selection only. An opponent receives a sequence of permitted backs and highlighted positions. Their active faces and internal card IDs are absent. The common deck reveals its next back, and the Shuler gets its next active face.

## Acknowledgements and snapshots

For bound seats, `n` is a monotonically increasing safe integer. A duplicate in the last 64 requests receives its prior `ack` without executing again. An older unknown number is rejected. `ack` contains `n`, `ok`, the current room `revision` and, on failure, an error code such as `stale`, `rejected`, `forbidden` or `maintenance`. Stale game commands receive a fresh snapshot.

`state` includes the room `revision`, the domain `tableRevision`, round ID `game`, `phase`, `serverTime`, and an authoritative `deadline` when applicable. Send the last `tableRevision` as request `revision`. Play commands require the same table revision and round. Independent shop and draft actions can use an older revision within the same round and phase after domain validation. Hand gestures do not advance the table revision. The compatibility projection `st` powers the classic renderer. Full snapshots are used for resync and reconnect.

Production limits include 32 KiB per inbound packet, 40 messages per second per connection, bounded acknowledgement caches, and disconnecting a slow consumer with excessive queued data. Identifiers and tokens use server-side cryptographic randomness. Log and event fields intended for a single seat are filtered from the shared projection.

## Operational checks

- `GET /healthz` is a loopback check used by the publisher. It reports protocol version, maintenance state and active match count.
- When the configured drain file exists, new starts are refused. Current commands, presence, and resume remain available until the last active match ends.
- The running server keeps rooms in memory. Completed-match statistics are stored separately in SQLite. Restarting the process outside a drained release ends in-memory rooms.
- Run `node tools/load-network.mjs 24 12` for the loopback benchmark. It reports request and reconnect percentiles, process memory and resource counts after closure. This measures the local Node server without TLS or browser rendering.
